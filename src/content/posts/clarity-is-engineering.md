遇到复杂问题时，人很容易立刻开始搜索、改代码、重启服务，然后在几十个变量之间来回跳跃。忙了很久，却很难说清楚究竟是哪一步起了作用。

更可靠的方法不是更快地尝试，而是先让问题变得可描述。

## 从可复现开始

一个问题如果不能稳定复现，就很难稳定修好。先把环境缩小到足够简单：

```text
输入 → 可观察的处理过程 → 错误结果
```

记录版本、入口、最小输入和实际输出。暂时移走与问题无关的配置，让每一次实验都回答一个明确问题。

## 一次只改变一个变量

当多个改动同时出现时，即使结果变好了，也无法确定原因。工程上的耐心通常体现在这里：

```js
const experiment = {
  hypothesis: '缓存键没有包含用户语言',
  change: '只把语言加入缓存键',
  expected: '切换语言后返回对应内容',
};
```

假设、改动、预期结果应该能用一句话分别说明。如果一句话装不下，说明实验还可以继续拆分。

## 把证据放在结论前面

“看起来正常”不是验证。真正有用的验证需要覆盖决定性路径：

- 请求是否到达了预期入口；
- 关键状态是否按预期改变；
- 用户最终看到的结果是否正确；
- 清空缓存或重新启动后是否仍然成立。

修复完成后，再从一个干净基线重跑最短路径。这样留下的不只是一段能工作的代码，还有一份以后可以依赖的证据。

## 写给未来的自己

清楚的提交信息、简短的复现脚本和几条关键日志，都是写给未来自己的说明书。它们会在数周之后，帮助我们避免重新经历同一段混乱。

复杂问题不会因此消失，但它会从一团模糊的感觉，变成一串可以逐项处理的事实。这本身就是一种重要的工程能力。
